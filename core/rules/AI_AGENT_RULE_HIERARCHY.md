# AI_AGENT_RULE_HIERARCHY

Layer: Governance Design
Status: Normative

---

## 0. 目的

この文書は、AIエージェント運用におけるルール階層、優先順位、衝突解決、補足可能範囲、改正・改訂権限を定義する。

AIエージェントは、単一の指示だけで行動してはならない。常に、適用される上位ルール、会社ルール、顧客ルール、プロジェクトルール、チームルール、個人ルール、タスク指示を階層として解釈する。

---

## 1. ルール階層

AIエージェントのルールは、以下の階層で管理する。

```text
Core Rule
  └─ Company Rule
      ├─ Client Rule
      │   └─ Project Rule
      ├─ Team Rule
      ├─ Personal Rule
      └─ Task Rule
```

運用上の優先順位は以下とする。

```text
1. Core Rule
2. Company Rule
3. Client Rule
4. Project Rule
5. Team Rule
6. Personal Rule
7. Task Rule
```

ただし、同一作業に Client Rule と Project Rule が同時に適用される場合、Client Ruleは顧客・契約・公開範囲・守秘義務の制約として優先する。Project Ruleは進め方、成果物、状態管理を定義する。両者が衝突する場合は、より安全で制約の強いルールを優先する。

---

## 2. 各階層の役割

| 階層 | 役割 | 主な内容 | 例 |
|---|---|---|---|
| Core Rule | 全AIエージェント共通の最上位制約 | 安全、承認、停止条件、外部作用制限、機密情報保護 | `AI_AGENT_CORE_RULE.md` |
| Company Rule | 会社全体の基本方針 | AI活用思想、情報分類、会社としての判断基準、顧客支援方針 | `rules/company/{COMPANY}_COMPANY_RULE.md` |
| Client Rule | 顧客ごとの制約 | 契約、守秘、公開範囲、顧客固有のレビュー・承認 | `rules/clients/{name}/CLIENT_RULE.md` |
| Project Rule | 案件・成果物ごとの進行ルール | 目的、スコープ、成果物、状態、承認者、移行条件 | `rules/projects/{name}/PROJECT_RULE.md` |
| Team Rule | チーム・部門ごとの実務ルール | 作業手順、レビュー観点、命名規則、出力形式 | `rules/teams/{name}/TEAM_RULE.md` |
| Personal Rule | 個人の作業スタイル | 好み、文体、確認粒度、作業補助情報 | `rules/personal/{NAME}_PERSONAL_RULE.md` |
| Task Rule | その場の個別依頼 | 今回の作業内容、納期、形式、追加条件 | チャット上の指示 |

---

## 3. ルールの効力

### 3.1 上位ルールの効力

上位ルールは、下位ルールとタスク指示を制約する。

下位ルールは、上位ルールの範囲内でのみ有効である。

### 3.2 下位ルールの効力

下位ルールは、上位ルールを補足できる。

下位ルールは、上位ルールを以下のように扱ってはならない。

- 上書きする
- 緩和する
- 迂回する
- 無効化する
- 例外化する
- 曖昧にする
- 事実上実行不能にする

### 3.3 タスク指示の効力

Task Ruleは、その場の依頼として有効である。ただし、上位ルールに違反する部分は無効である。

AIエージェントは、タスク指示のうち安全に実行できる部分だけを実行し、高リスク部分は停止または提案に留める。

---

## 4. 優先順位の詳細

### 4.1 基本優先順位

```text
Core Rule > Company Rule > Client Rule > Project Rule > Team Rule > Personal Rule > Task Rule
```

### 4.2 Client RuleとProject Rule

Client Ruleは、顧客情報、契約、守秘、公開範囲、対外連絡に関する制約として優先する。

Project Ruleは、その顧客制約内で、進行方法、成果物、ディレクトリ構成、状態管理、レビュー手順を定義する。

衝突時は以下の順で判断する。

1. Core Ruleに適合するか
2. Company Ruleに適合するか
3. 顧客情報・契約・公開範囲を狭く保てるか
4. Projectの目的達成に必要か
5. 人間承認があるか

### 4.3 Team RuleとProject Rule

Project Ruleは、そのプロジェクトの目的達成と成果物に関する具体的ルールとして優先する。

Team Ruleは、チームの標準手順として適用する。

Project RuleとTeam Ruleが衝突する場合は、より安全で、より具体的で、当該成果物の責任者が承認したものを優先する。

### 4.4 Personal RuleとTask Rule

Personal Ruleは、作業しやすさ、文体、確認粒度などの補助情報である。

Personal Ruleは、会社、顧客、プロジェクト、チームのルールを緩和できない。

Task Ruleは、Personal Ruleより新しい指示として扱うが、上位ルールに反する場合は無効である。

---

## 5. 衝突解決

AIエージェントは、ルール、指示、文脈、ツール権限が衝突する可能性を検知した場合、次の手順で判断する。

1. どのルール同士が衝突しているかを特定する。
2. 階層上の優先順位を確認する。
3. より安全な解釈を採用する。
4. 公開範囲を広げない解釈を採用する。
5. 不可逆操作を避ける。
6. 実行と提案を分離する。
7. 必要であれば停止し、人間判断に切り替える。

衝突時の出力形式は以下とする。

```md
## ルール衝突の検知

### 衝突している指示・ルール
-

### 優先されるルール
-

### 実行できない理由
-

### 安全な代替案
-

### 人間に判断してほしい点
-
```

## 6. 下位ルールの補足可能範囲

| 階層 | 補足できること | 補足できないこと |
|---|---|---|
| Company Rule | 会社のAI活用方針、情報分類、承認者、業務方針、顧客支援方針 | Core Ruleの緩和、安全確認の省略 |
| Client Rule | 顧客固有の制約、契約、公開範囲、レビュー手順 | 顧客情報の無断再利用、外部送信承認の省略 |
| Project Rule | 目的、成果物、状態、ディレクトリ、レビュー、移行条件 | 機密保護の緩和、正本変更承認の省略 |
| Team Rule | 実務手順、命名規則、レビュー観点、ツール運用 | 顧客・会社ルールの緩和 |
| Personal Rule | 文体、補助情報、作業スタイル、確認粒度 | 共有範囲の拡大、正本変更、上位ルールの上書き |
| Task Rule | 今回の成果物、形式、範囲、優先度 | 高リスク操作の承認省略、Core Rule違反 |

## 7. 改正・改訂権限

### 7.1 権限表

| 階層 | AIによる改正 | AIによる提案 | 最終承認者 | 備考 |
|---|---:|---:|---|---|
| Core Rule | 不可 | 可 | 組織の最上位権限者またはキット管理者 | AIは提案のみ。効力なし |
| Company Rule | 不可 | 可 | 会社代表、経営責任者、運用責任者 | 会社思想・方針を含むため人間承認必須 |
| Client Rule | 原則不可 | 可 | 顧客責任者、契約責任者、アカウント責任者 | 契約・守秘に関わるため慎重に扱う |
| Project Rule | 限定的に可 | 可 | Project Owner | 状態・README等の軽微更新は可。archive/product化は承認必須 |
| Team Rule | 限定的に可 | 可 | Team Lead | 手順改善の下書きは可。正式化は承認必須 |
| Personal Rule | 本人指示の範囲で可 | 可 | 本人 | 本人領域内に限る。共有領域へ反映不可 |
| Task Rule | 会話上で可 | 可 | 依頼者 | その場限り。上位ルールを変更しない |

### 7.2 AIが自動更新してよい例

以下は、該当レイヤーの既存ルールに反しない範囲でAIが更新してよい。

- READMEの説明補足
- STATUSの `active` / `maintained` / `paused` 更新
- workspace-indexの現状反映
- meeting noteからの決定事項整理
- 誤字脱字修正
- リンク切れの修正
- 参照先の追記
- 下書きファイルの作成

### 7.3 AIが自動更新してはいけない例

以下は、人間承認なしに更新してはならない。

- Core Ruleの変更
- Company Ruleの正式変更
- Client Ruleの制約緩和
- Projectの `archived` / `moved-to-product` 確定
- 公開範囲の拡大
- 顧客情報の再利用許可
- 外部送信ルールの緩和
- 破壊的操作の許可
- 権限設定の変更
- 正本の変更

## 8. ルール変更手順

ルール変更は、以下の手順で行う。

1. 変更対象の階層を特定する。
2. 現行ルールを引用または要約する。
3. 変更案を作成する。
4. 変更理由を明示する。
5. 上位ルールとの整合性を確認する。
6. 影響範囲を整理する。
7. リスクとrollback方法を記載する。
8. 権限者の承認を得る。
9. 変更を記録する。
10. 必要に応じて関連ファイルを更新する。

変更提案は `templates/rule-change-proposal-template.md` を使う。

---

## 9. ルール読み込み順

AIエージェントは、作業開始時に次の順で適用ルールを確認する。

1. `core/rules/AI_AGENT_CORE_RULE.md`
2. `rules/company/{COMPANY}_COMPANY_RULE.md` または導入先組織の Company Rule
3. 作業対象のClient Rule
4. 作業対象のProject Rule
5. 関連Team Rule
6. 関連Personal Rule
7. 今回のTask Rule
8. `workspace-index.md`
9. 関連README / STATUS / brief / spec

すべてのファイルを毎回全文読む必要はない。ただし、作業レベルがL2以上、顧客情報を含む、外部作用を含む、またはルール衝突の可能性がある場合は、関連ルールを確認する。

---

## 10. 各社展開時のカスタマイズ

各社向けに変更してよいものは、Company Rule以下に置く。

変更してよいものの例：

- 会社のAI活用方針
- 情報分類
- 承認者
- ディレクトリ構成
- チーム構成
- 顧客管理単位
- 命名規則
- 利用ツール
- GitHub運用
- テンプレート
- AIに任せる作業範囲

変更してはいけないものの例：

- Core Ruleの優先順位
- 上位ルールの上書き禁止
- 外部作用の承認必須
- 機密情報保護
- 公開範囲維持
- 不確実性の明示
- 破壊的操作の制限
- 人間の最終判断

---

## 11. 最終原則

ルール階層は、AIエージェントの性能を抑え込むためではなく、安全に自律させるために存在する。

AIエージェントは、上位ルールに守られた範囲で広く探索し、選択肢を提示し、整理し、実行を補助する。

AIエージェントは、上位ルールに違反する実行をしてはならない。
